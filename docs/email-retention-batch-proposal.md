# メールデータ定期削除バッチの提案

## 1. 目的と背景

このアプリは、メールで届いた情報を共有し、見やすく表示するための社内ツールである。現在はPower AutomateのサブシステムがDBに直接データを登録しており、データが継続的に増加する。

元メールは別途存在し、アプリ上のデータやNJK記入欄を残し続ける必要はない。そのため、受信から1年を過ぎたデータを定期削除し、不要なデータの蓄積を抑える。

本資料は実装前の提案である。合意済みの要件と、具体化のための設計案・事前確認事項を以下に整理する。

## 2. 合意済みの要件

| 項目 | 方針 |
| --- | --- |
| 保存期間 | 受信から1年 |
| 対象 | 問い合わせメールと求人関連メール |
| 判定日時 | 受信日時 `received_at` |
| フラグ | 閲覧済み・NJK記入済みなどのフラグにかかわらず削除する |
| NJK記入欄 | メールのレコードと一緒に削除してよい |
| 削除方式 | 対象レコードを物理削除する |
| 実行方法 | Flaskのカスタムコマンドとして作成する |
| 事前確認 | `--dry-run` で削除せずに対象を確認できること |
| 大量データへの対応 | 一度に全件削除せず、分割して処理する |

削除処理はデータ取り込みと独立させる。Power AutomateをPythonへ置き換える計画は保留とし、今回の対象に含めない。

## 3. 現行コードから確認できること

- `app/models.py` に `ContactEmail` と `JobEmail` が定義されている。
- 対応するテーブルは `contact_emails` と `job_emails` である。
- 両テーブルに受信日時 `received_at` と、そのインデックスが定義されている。
- `app/__init__.py` の `create_app()` でFlaskアプリとDB接続を初期化している。
- `config.py` では `DATABASE_URL` を使用し、アプリのタイムゾーンは `Asia/Tokyo` としている。
- 現在の画面操作にはメモ保存、閲覧済みフラグの更新、個別削除がある。

実稼働DBの製品・バージョン・ストレージエンジン・分離レベル、および実テーブルのインデックスは未確認である。後述のロック動作はMySQL / InnoDBを前提とする。

## 4. 削除コマンドの設計案

### 4.1 起動方法

Flaskのカスタムコマンドに既存の設定とSQLAlchemyのDB接続を利用させる。Web画面やHTTPリクエストを経由せず、独立したプロセスとして実行する。

コマンド名は `purge-old-emails` を案とする。以下は実装後の利用イメージであり、現時点では実行できない。

```bash
# 削除対象の確認
flask --app 'app:create_app("production")' purge-old-emails --dry-run

# 削除の実行
flask --app 'app:create_app("production")' purge-old-emails

# 1回の削除件数を指定する例
flask --app 'app:create_app("production")' purge-old-emails --batch-size 1000
```

実行環境はファクトリ引数で明示し、仮想環境と必要な設定値を読み込ませる。現在の初期化では `SECRET_KEY` も必要になる。

### 4.2 保存期間と境界

「受信から1年」の具体的な計算は、次を設計案とする。

- 実行開始時の日本時間を1回取得し、暦年で1年前の日時を削除基準とする。固定の365日前とは区別する。
- `received_at < 削除基準日時` のレコードを削除する。基準日時と完全一致するレコードは残す。
- 実行日が2月29日の場合、前年2月28日の同時刻を基準とする。
- 1回の実行中は、両テーブルを通して同じ基準日時を使用する。
- `created_at`、`updated_at`、各種フラグ、メモの有無は判定に使用しない。

例：2026年11月2日 00:00 JSTに開始した場合、2025年11月2日 00:00 JSTより前に受信したデータが対象となる。

DBの日時列はタイムゾーン情報を持たない定義のため、Power Automateが実際に保存する日時の基準を確認し、日本時間との比較にずれが生じないようにする。

定期実行の間隔やWSLの停止期間によっては、1年を超えたデータが次の実行まで残る。保存期間を超えた瞬間に削除する仕組みではない。

### 4.3 分割削除

1. バッチの多重実行を防ぐためのロックを取得する。
2. 実行開始時刻と削除基準日時を確定する。
3. 対象テーブルから、削除条件を満たすIDを一定件数取得する。
4. 取得したIDと削除基準日時を条件に、SQLAlchemyで一括DELETEする。
5. その単位でコミットし、実際に削除した件数を記録する。
6. 対象IDがなくなるまで繰り返し、もう一方のテーブルも処理する。
7. 集計を出力し、ロックを解放して終了する。

初期の分割件数は1,000件を案とし、正の整数として指定可能にする。実環境の負荷に応じて調整する。

取得順を固定し、`OFFSET` は使用しない。削除のたびに対象件数が減るため、`OFFSET` で位置を進めると未処理データを飛ばしてしまう可能性がある。

メール本文などを全件読み込んで1件ずつ削除する処理は行わない。削除時にも日時条件を付け、ID取得後に受信日時が変更された場合は条件を再評価する。競合による削除件数0だけを終了条件にせず、次の対象を確認する。

途中までのコミットは保持する。後続処理で失敗しても、再実行すれば残っている対象を処理できる設計とする。全テーブルをまとめて1つのトランザクションにはしない。

### 4.4 dry-run

`--dry-run` ではデータを変更せず、以下を表示する。

- 実行環境と削除基準日時・タイムゾーン
- テーブルごとの対象件数と合計件数
- 設定された分割件数

DELETEは実行しない。確認中も取り込みや手動削除が可能なため、表示件数と後日の実削除件数が一致する保証はない。

## 5. 定期実行の設計案

### 5.1 systemdによる起動

WSL 2のUbuntu 24.04 LTSまたは26.04 LTS上で、systemdが利用可能かつ有効であることを確認する。削除コマンドを起動する `Type=oneshot` のserviceと、定期起動するtimerを用意する。

実行時刻は毎日日本時間の0時を案とする。timerの主要設定は以下を想定する。

```ini
[Timer]
OnCalendar=*-*-* 00:00:00 Asia/Tokyo
Persistent=true

[Install]
WantedBy=timers.target
```

これはtimerの設定案であり、対応するserviceの作成とtimerの有効化が別途必要である。serviceには実行ユーザー、作業ディレクトリ、仮想環境内の実行ファイル、設定の読み込み方法を明示する。定期実行用途では `RemainAfterExit=yes` を設定しない。

### 5.2 停止中・失敗時の動作

| 状態 | 動作 |
| --- | --- |
| FlaskのWebサーバーだけが停止 | DBとアプリ設定が正常なら、削除コマンドは独立して実行できる |
| 指定時刻にWSLが停止 | その時刻には実行できない。`Persistent=true` により、次回起動後にtimerが有効になった際、実行漏れを補う |
| WSLが数日停止 | 実行漏れを1回の起動で補い、その時点で保存期間を過ぎたデータを処理する |
| DB停止・接続失敗 | バッチは失敗を記録して異常終了する。`Persistent=true` 自体には失敗時の再試行機能はない |

timerは停止中のWindowsやWSLを自動起動する仕組みではない。また、systemdサービスを登録するだけでWSLの常時起動が保証されるわけではない。今回の用途では、次回起動後に削除を追いつかせる運用を想定する。

## 6. DB操作との競合と排他制御

### 6.1 通常操作との並行実行

取り込みと画面操作を継続しながら削除する。MySQL / InnoDBでは、競合する更新・削除をDBのロックで調整する。

| 重なる操作 | 想定される動作 |
| --- | --- |
| Power Automateによる新着追加 | 通常は並行実行可能。ただし、SQLやロック範囲により待機する場合がある |
| 一覧・詳細の通常のSELECT | 一般的な分離レベルでは、通常は削除完了を待たずに読み取り可能 |
| 削除対象と同じメールの更新・削除 | 先行する処理のロック解除を待つ。結果として対象が消えている場合もある |

ロック範囲はSQL、インデックス、分離レベルによって変わる。日付による広い範囲のDELETEは範囲のロックを伴う場合があるため、対象IDを取得して主キーを指定する削除と、短いトランザクションを基本とする。実行計画を確認し、分割すれば必ず対象行だけをロックするとは断定しない。

Flaskプロセス内のロックだけでは、DBへ直接接続するPower Automateとの排他はできない。通常操作との整合性はDBのトランザクションとロックで保つ。

### 6.2 ロック待ち・デッドロック

- ロック待ち時間超過またはデッドロック時は、その処理単位を明示的にロールバックする。
- 少し待ってから、対象IDの再取得を含めて回数制限付きで再試行する。
- 上限を超えた場合は、既にコミットした件数を含むログを残し、異常終了する。
- DB接続失敗など、その他のエラーまで無条件に再試行しない。

再試行回数、待機時間、ロック待ち時間の具体値は実装時に定める。バッチ側の再試行だけで、Power AutomateやWeb側に発生する競合エラーまで解消されるわけではないため、並行実行を検証する。

### 6.3 削除バッチ同士の多重実行

同じsystemdサービスは、実行中にtimerから再度起動されても別インスタンスとして重複起動されない。ただし、Flaskコマンドの直接実行や別ホストからの実行は別途考慮が必要である。

コマンド側にも多重実行防止を設け、取得できなければ削除を開始せず、既に実行中である旨を記録して終了する方針とする。方式は配置構成に合わせて決める。

- 同一WSL内だけで実行する場合：共通のファイルロックを候補とする。
- 複数ホストから実行し得る場合：MySQLの名前付きロックなど、DBを共有する実行元間で有効な方式を検討する。

このロックは削除バッチ同士の重複を防ぐためのものであり、Power Automateや画面操作全体を停止させるものではない。

### 6.4 閲覧・編集途中の削除

利用者がメールを開いている間に、そのレコードが削除される場合がある。閲覧中・編集中でも保存期間を超えたデータは削除対象とする。

画面側では、更新・個別削除・閲覧済み更新の対象がなくなった場合に、未処理の例外による500エラーにならないようにする。「対象メールは削除されました」などを案内し、一覧へ戻れる動作を検討する。最初に取得できてもコミット前に削除される場合があるため、保存時の競合も扱う。

### 6.5 DBエラー・接続切断

既にコミットした分の削除は保持し、エラーが発生した処理単位の未確定分はロールバックする。接続切断でロールバックを送れない場合は、DB側で接続終了を認識した際に未コミットのトランザクションが取り消される。接続終了の認識までは、ロックが残る場合がある。

ただし、コミット中に接続が切れた場合は、DBでは削除が確定していても、バッチが成功応答を受け取れていない可能性がある。この場合は「コミット結果不明」と記録し、成功応答を確認できた件数と区別する。失敗したから必ず未削除であるとは扱わない。

DB停止・接続切断時は無条件に再接続して処理を続けず、後続の削除を中止して異常終了する。セッションと多重実行防止ロックの後始末を行い、その際のエラーが元のエラーを隠さないようにする。SQLAlchemyの接続管理だけで、処理途中のトランザクションが自動復旧するわけではない。

DB復旧後の手動実行、または次回の定期実行で、残っている対象を取得し直す。削除済みの行は再取得されないため、コミット結果が不明だった場合も、残りの対象を処理できる。

## 7. ログと運用

ログには実行開始・終了、実行環境、削除基準日時、dry-runの有無、テーブル別の対象件数または実削除件数、所要時間、再試行、エラーを記録する。メール本文やメールアドレスなどの内容は出力しない。

通常実行では成功と失敗を終了コードで区別する。多重実行を検知して処理を見送った場合は、その理由を明示する。systemd経由の実行結果は `systemctl` と `journalctl` で確認できるようにする。

導入は次の順で進める。

1. 実稼働DB・日時基準・systemdの利用可否を確認する。
2. コマンド、競合時の処理、service / timerの設定例を実装する。
3. テスト環境で境界条件と並行実行を検証する。
4. 実環境で `--dry-run` を実行し、基準日時と対象件数を確認する。
5. 初回の蓄積分を分割削除し、負荷とログを確認する。
6. timerを有効化し、次回予定と実行結果を確認する。

### 7.1 実装と導入の進め方

コードの実装と自動テストは、1回のセッションで対応できる規模と見込む。機能ごとにセッションを細かく分けることは必須とせず、次の2段階で進める。

| 段階 | 作業内容 | 完了の目安 |
| --- | --- | --- |
| 第1段階：実装・自動テスト | Flaskコマンド、保存期間の判定、分割削除、dry-run、多重実行防止、エラー処理・再試行、ログ、`tests/` 以下の自動テスト、systemdのservice / timer設定例、関連文書をまとめて作成する | 1セッションを目安に、レビュー可能な実装一式と自動テストの実行結果をそろえる |
| 第2段階：実環境での確認・導入 | 実稼働DBと日時基準・WSL設定を確認し、同じDBエンジンのテスト専用環境でロック・接続障害・並行実行を検証する。実環境でdry-run、初回削除、timerの有効化と実行結果確認を行う | 環境固有の動作と実行結果を確認したうえで定期運用を開始する |

SQLiteと例外の模擬を使う自動テストだけでは、MySQL / InnoDBの実際のロックや接続切断の挙動まで確認できないため、実環境への導入は次の段階として扱う。第1段階の完了を、そのまま実環境での検証完了や定期運用開始とはしない。

1セッションは作業量の目安であり、環境依存の問題や追加の確認事項が見つかった場合は分けて進める。現段階では提案資料の整備までとし、実装・テストコードの作成は保留する。

## 8. 検証観点

### 8.1 基本動作と実環境での検証

- 両テーブルで、保存期間内・境界一致のデータが残り、基準より前のデータだけが削除される。
- 暦年の計算、うるう日、日本時間とDB日時の扱いが設計どおりである。
- フラグやメモの有無によって対象が変わらない。
- dry-runでデータが変更されず、基準と件数が表示される。
- 分割件数を超えるデータが取りこぼしなく削除され、対象0件でも正常終了する。
- 途中失敗時に処理単位がロールバックされ、再実行で残りを処理できる。
- ロック競合時の再試行回数・待機・異常終了が設計どおりである。
- 手動実行を含む多重起動を検知できる。
- 取り込み・通常の読み取り・同一メールの更新や削除との並行実行を確認する。
- WSL停止中の実行漏れが、次回起動後のtimer有効化時に補われる。

ロック・デッドロックの検証は実稼働と同じDBエンジンで行う。既存テスト用のSQLiteだけではMySQL / InnoDBの動作を検証できない。

### 8.2 DBエラー時の簡単な自動テストの追加計画

削除コマンドの実装に合わせて、`tests/test_email_retention.py`（仮称）にpytestのテストを追加する。現段階では計画の追記のみとし、テストコードや削除処理の作成は保留する。

既存の `app`、`db_session` フィクスチャとテスト専用のインメモリSQLiteを利用し、実際の削除処理・Flaskコマンドを呼び出す。少量のデータと小さな分割件数を使い、削除実行やコミットのタイミングで例外を発生させる。テスト専用に削除処理のコピーを作って、そのコピーだけを検証する構成にはしない。

| テスト | 確認する結果 |
| --- | --- |
| 途中の処理単位で、DELETE後・コミット前にエラー | 先にコミットした分だけが削除済みとなり、エラーが発生した単位はロールバックされ、後続分は残る |
| 対象取得・DELETE時の接続エラーを模擬 | 後続処理を中止し、エラーを記録して非0の終了コードを返す |
| エラーを解除して再実行 | 残っている古いデータが削除され、保存期間内のデータは残る |
| ロック待ち時間超過・デッドロックを模擬 | 設定回数以内で再試行し、上限到達時は異常終了する |
| DBではコミット済みだが成功応答が得られない状態を模擬 | 結果不明をログに残し、その単位を成功確認済み件数に加えない。再実行で残りを処理できる |

ロールバックの確認では、DELETE前に例外を出すだけでなく、DELETEが実行された後に失敗させ、未確定の削除が取り消されることをDBの内容で確認する。実行後はセッションを取り直し、DBの状態を検証する。

例外の模擬によって確認できるのは、アプリ側のエラー処理・処理中断・再実行の動作である。MySQLの実際の切断検知、ロック解除のタイミング、デッドロック、コミット中の通信障害の挙動を保証するものではない。これらは別途、実稼働と同じDBエンジンを使うテスト専用環境で検証する。
