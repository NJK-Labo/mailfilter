# メールデータ定期削除バッチの提案

## 1. 目的と背景

このアプリは、メールで届いた情報を共有し、見やすく表示するための社内ツールである。現在はPower AutomateのサブシステムがDBに直接データを登録しており、データが継続的に増加する。

元メールは別途存在し、アプリ上のデータやNJK記入欄を残し続ける必要はない。そのため、受信から1年を過ぎたデータを定期削除し、不要なデータの蓄積を抑える。

本資料は実装前の提案である。合意済みの要件と設計案・事前確認事項を整理する。現段階では資料の整備までとし、削除処理・テストコードの作成は保留する。

## 2. 合意済みの要件

| 項目 | 方針 |
| --- | --- |
| 保存期間 | 受信から暦年で1年。境界と2月29日の扱いは4.2節 |
| 対象 | 問い合わせメールと求人関連メール |
| 判定日時 | 受信日時 `received_at` |
| フラグ | 閲覧済み・NJK記入済みなどのフラグにかかわらず削除する |
| NJK記入欄 | メールのレコードと一緒に削除してよい |
| 削除方式 | 対象レコードを物理削除する |
| 実行方法 | Flaskのカスタムコマンドとして作成する |
| 事前確認 | `--dry-run` で削除せずに対象を確認できること |
| 大量データへの対応 | 初期値1,000件で分割して処理する。導入時の実測で調整する |
| 多重実行防止 | 同一WSL内でOSの `flock` を利用する。詳細は6.3節 |
| 定期実行 | 毎日0時JST、`systemd.timer`、`Persistent=true` を採用する |
| 実行時間上限 | systemd経由の実行は暫定5分。導入時の実測で確認する |
| 異常時の運用 | ログに記録し、異常がある場合は社内の担当者が確認する |

削除処理はデータ取り込みと独立させる。Power AutomateをPythonへ置き換える計画は保留とし、今回の対象に含めない。

## 3. 現行コードから確認できること

- `app/models.py` に `ContactEmail`（`contact_emails`）と `JobEmail`（`job_emails`）が定義されている。
- 両テーブルに受信日時 `received_at` と、そのインデックスが定義されている。
- `app/__init__.py` の `create_app()` でFlaskアプリとDB接続を初期化している。
- `config.py` では `DATABASE_URL` を使用し、アプリのタイムゾーンは `Asia/Tokyo` としている。
- 現在の画面操作にはメモ保存、閲覧済みフラグの更新、個別削除がある。

実稼働DBの製品・バージョン・ストレージエンジン・分離レベル、および実テーブルのインデックスは未確認である。後述のDBのロック動作はMySQL / InnoDBを前提とする。

## 4. 削除コマンドの設計

### 4.1 起動方法

Flaskのカスタムコマンドに既存の設定とSQLAlchemyのDB接続を利用させる。Web画面やHTTPリクエストを経由せず、独立したプロセスとして実行する。

コマンド名は `purge-old-emails` を案とする。以下は実装後の利用イメージであり、現時点では実行できない。

```bash
# 削除対象の確認
flask --app 'app:create_app("production")' purge-old-emails --dry-run

# 削除の実行
flask --app 'app:create_app("production")' purge-old-emails

# 1回の削除件数を指定する例
flask --app 'app:create_app("production")' purge-old-emails --batch-size 1000
```

実行環境はファクトリ引数で明示し、仮想環境と必要な設定値を読み込ませる。現在の初期化では `SECRET_KEY` も必要になる。

### 4.2 保存期間と境界

「受信から1年」の計算と削除の境界は、次のとおりとする。

- 実行開始時の日本時間を1回取得し、暦年で1年前の日時を削除基準とする。固定の365日前とは区別する。
- `received_at < 削除基準日時` のレコードを削除する。基準日時と完全一致するレコードは残す。
- 実行日が2月29日の場合、前年2月28日の同時刻を基準とする。
- 1回の実行中は、両テーブルを通して同じ基準日時を使用する。
- `created_at`、`updated_at`、各種フラグ、メモの有無は判定に使用しない。

例：2026年11月2日 00:00 JSTに開始した場合、2025年11月2日 00:00 JSTより前に受信したデータが対象となる。

DBの日時列はタイムゾーン情報を持たない定義のため、Power Automateが実際に保存する日時の基準を確認し、日本時間との比較にずれが生じないようにする。

定期実行の間隔やWSLの停止期間によっては、1年を超えたデータが次の実行まで残る。保存期間を超えた瞬間に削除する仕組みではない。

### 4.3 分割削除

1. 6.3節のファイルロックを取得する。取得できた場合だけ後続の処理に進む。
2. 実行開始時刻と削除基準日時を確定する。
3. 対象テーブルから、削除条件を満たすIDを一定件数取得する。
4. 取得したIDと削除基準日時を条件に、SQLAlchemyで一括DELETEする。
5. その単位でコミットし、実際に削除した件数を記録する。
6. 対象IDがなくなるまで繰り返し、もう一方のテーブルも処理する。
7. 集計を出力し、ロックを解放して終了する。

分割件数の初期値は1,000件とし、正の整数として指定可能にする。導入時の実測と実環境の負荷に応じて調整する。

取得順を固定し、削除による取りこぼしを防ぐため `OFFSET` は使用しない。

メール本文などを全件読み込んで1件ずつ削除する処理は行わない。削除時にも日時条件を付け、ID取得後に受信日時が変更された場合は条件を再評価する。競合による削除件数0だけを終了条件にせず、次の対象を確認する。

全テーブルをまとめて1つのトランザクションにはしない。途中失敗時の扱いは6.5節に従う。

### 4.4 dry-run

`--dry-run` ではデータを変更せず、以下を表示する。

- 実行環境と削除基準日時・タイムゾーン
- テーブルごとの対象件数と合計件数
- 設定された分割件数

ファイルロックは取得せず、削除バッチの実行中でも確認できる。確認中も取り込みや削除が行われるため、表示件数と実削除件数は一致するとは限らない。

## 5. 定期実行の設計

### 5.1 systemdによる起動

WSL 2のUbuntu 24.04 LTSまたは26.04 LTS上で、systemdが利用可能かつ有効であることを確認する。削除コマンドを起動する `Type=oneshot` のserviceと、定期起動するtimerを用意する。

実行時刻は毎日日本時間の0時とし、`systemd.timer` と `Persistent=true` を採用する。timerの主要設定は以下のとおり。

```ini
[Timer]
OnCalendar=*-*-* 00:00:00 Asia/Tokyo
Persistent=true

[Install]
WantedBy=timers.target
```

対応するserviceには実行ユーザー、作業ディレクトリ、仮想環境内の実行ファイル、設定の読み込み方法を明示する。定期実行用途では `RemainAfterExit=yes` を設定しない。

serviceの `[Service]` に `TimeoutStartSec=5min` を設定し、DBのロック待ち・再試行を含めた全体の暫定上限を5分とする。導入時に通常の対象件数と初回・長期停止後の蓄積分で所要時間を実測し、問題がなければ採用する。必要な調整は実測結果に基づいて行う。

### 5.2 停止中・失敗時の動作

| 状態 | 動作 |
| --- | --- |
| FlaskのWebサーバーだけが停止 | DBとアプリ設定が正常なら、削除コマンドは独立して実行できる |
| 指定時刻にWSLが停止（数日間の停止を含む） | 停止中は実行できない。`Persistent=true` により、次回起動後のtimer有効化時に1回実行し、その時点の削除対象を処理する |
| DB停止・接続失敗 | バッチは失敗を記録して異常終了する。`Persistent=true` 自体には失敗時の再試行機能はない |
| バッチ全体が5分を超過 | systemdがserviceの停止処理を行い、失敗をログに記録する。停止猶予は実装時に定め、DB状態と再実行は6.5節に従う |

timerは停止中のWindowsやWSLを自動起動せず、serviceの登録もWSLの常時起動を保証しない。次回起動後に削除を追いつかせる運用とする。

## 6. DB操作との競合と排他制御

### 6.1 通常操作との並行実行

取り込みと画面操作を継続しながら削除する。MySQL / InnoDBでは、競合する更新・削除をDBのロックで調整する。

| 重なる操作 | 想定される動作 |
| --- | --- |
| Power Automateによる新着追加 | 通常は並行実行可能。ただし、SQLやロック範囲により待機する場合がある |
| 一覧・詳細の通常のSELECT | 一般的な分離レベルでは、通常は削除完了を待たずに読み取り可能 |
| 削除対象と同じメールの更新・削除 | 先行する処理のロック解除を待つ。結果として対象が消えている場合もある |

ロック範囲はSQL、インデックス、分離レベルによって変わる。日付による広い範囲のDELETEは範囲のロックを伴う場合があるため、対象IDを取得して主キーを指定する削除と、短いトランザクションを基本とする。実行計画を確認し、分割すれば必ず対象行だけをロックするとは断定しない。

### 6.2 ロック待ち・デッドロック

- ロック待ち時間超過またはデッドロック時は、その処理単位を明示的にロールバックする。
- 少し待ってから、対象IDの再取得を含めて回数制限付きで再試行する。
- 上限を超えた場合は、既にコミットした件数を含むログを残し、異常終了する。
- DB接続失敗など、その他のエラーまで無条件に再試行しない。

DB接続・通信の待ち時間にも上限を設ける。再試行・待機・タイムアウトの具体値は全体上限5分を考慮して実装時に定める。バッチ側の再試行だけでPower AutomateやWeb側の競合エラーも解消されるとは限らないため、並行実行を検証する。

### 6.3 削除バッチ同士の多重実行

定期実行と手動実行は同一WSL内で行う前提とし、LinuxのOSが管理する `flock` によるファイルロックを採用する。同じsystemdサービスは重複起動されないが、Flaskコマンドの直接実行にも対応するため、コマンド内部でロックを取得する。

| 項目 | 方針 |
| --- | --- |
| ロックファイルの配置 | WSLのLinux側に共通の絶対パスを指定し、同じDBに対する定期実行と手動実行で共有する。具体的なパスは配置先に合わせて確定する |
| 実行ユーザー・権限 | 定期実行と手動実行は原則同じユーザーとし、ロックファイルを作成・オープンできるディレクトリとファイルの権限を設定する |
| 取得方法 | 排他ロックを待機なしで取得し、取得できた場合だけ削除処理に進む |
| 既にロックされている場合 | 削除せず、「既に実行中」とログに記録して終了コード0で正常終了する |
| 権限不足などの取得エラー | 多重実行とは区別し、エラーをログに記録する。削除せず、非0の終了コードで異常終了する |
| 保持期間 | 両テーブルの処理と集計が終わるまで保持する。分割ごとのコミットやDBエラー時の再試行の間も解放しない |
| 終了時 | 正常終了・例外による終了のいずれもロックを解放してファイルを閉じる。ファイルは削除・置換せず、同じものを使い続ける |

ロック状態はOSのロック取得結果で判定する。強制終了時も、保持しているファイル記述子がすべて閉じられるとOSがロックを解放する。dry-runは4.4節のとおり対象外とする。

このロックは、同じファイルのロックを取得する削除バッチ同士の重複を防ぐ。Power Automateや画面操作との競合は6.1節のDBのトランザクションとロックで扱う。将来、別ホストからも削除バッチを実行する構成に変える場合は、排他方式を見直す。

### 6.4 閲覧・編集途中の削除

利用者がメールを開いている間に、そのレコードが削除される場合がある。閲覧中・編集中でも保存期間を超えたデータは削除対象とする。

画面側では、更新・個別削除・閲覧済み更新の対象がなくなった場合に、未処理の例外による500エラーにならないようにする。「対象メールは削除されました」などを案内し、一覧へ戻れる動作を検討する。最初に取得できてもコミット前に削除される場合があるため、保存時の競合も扱う。

### 6.5 DBエラー・接続切断・処理中断

既にコミットした分の削除は保持し、エラーが発生した処理単位の未確定分はロールバックする。接続切断でロールバックを送れない場合は、DB側で接続終了を認識した際に未コミットのトランザクションが取り消される。接続終了の認識までは、ロックが残る場合がある。

コミット中の接続切断では、DBで削除が確定していても成功応答を受け取れていない可能性がある。この場合は「コミット結果不明」と記録し、成功確認済み件数と区別する。タイムアウトによる停止でも、コミット応答を確認できていない分を削除成功とは扱わない。

DB停止・接続切断時は後続の削除を中止して異常終了する。無条件の再接続は行わず、セッションとファイルロックの後始末を行う。その際のエラーが元のエラーを隠さないようにする。

DB復旧後やタイムアウトによる停止後は、担当者の確認後に手動実行するか、次回の定期実行で残りの対象を取得し直す。削除済みの行は再取得されないため、コミット結果が不明だった場合も再実行できる。

## 7. ログと導入手順

### 7.1 ログと運用

バッチの処理ログは、既存のロガー設定（`StreamHandler` による標準エラー出力）を利用する。実行開始・終了、実行環境、削除基準日時、dry-runの有無、テーブル別の対象件数または成功確認済み削除件数、所要時間、再試行、見送り理由、エラーを記録する。メール本文やメールアドレスなどの内容は出力しない。

正常終了は終了コード0、異常終了は非0とする。多重実行による見送りは6.3節に従う。

systemd経由では、標準出力・標準エラー出力をjournalに収集するようserviceを設定し、`journalctl` でアプリケーションのログを確認する。serviceの終了状態やタイムアウトによる停止は、`systemctl` と `journalctl` で確認する。

失敗を検知するための対応はログへの記録までとし、異常がある場合は社内の担当者がログを確認する運用とする。

## 8. 検証観点

### 8.1 基本動作の自動テスト

- 両テーブルで、保存期間内・境界一致のデータが残り、基準より前のデータだけが削除される。
- 暦年の計算、うるう日、日本時間とDB日時の扱いが設計どおりである。
- フラグやメモの有無によって対象が変わらない。
- dry-runでデータが変更されず、基準と件数が表示される。削除バッチがファイルロックを保持している間も実行できる。
- 分割件数を超えるデータが取りこぼしなく削除され、対象0件でも正常終了する。
- 手動実行を含む別プロセスからの多重起動を検知し、後から起動したバッチは待機・削除せず、理由をログに記録して終了コード0で終了する。
- 権限不足などのファイルロック取得エラーでは削除せず、エラーログと非0の終了コードを返す。
- 分割コミットや再試行の間もファイルロックを保持し、正常終了・例外・強制終了後に再取得できる。ロックファイルが残っていても次の実行を妨げない。

### 8.2 DBエラー時の自動テスト

`tests/test_email_retention.py`（仮称）にpytestのテストを追加する。既存の `app`、`db_session` フィクスチャとインメモリSQLiteを利用し、少量のデータと小さな分割件数で実際の削除処理・Flaskコマンドを呼び出す。DELETEやコミット時の例外を模擬し、テスト用に複製した処理だけを検証する構成は避ける。

| テスト | 確認する結果 |
| --- | --- |
| 途中の処理単位で、DELETE後・コミット前にエラー | 先にコミットした分だけが削除済みとなり、エラーが発生した単位はロールバックされ、後続分は残る |
| 対象取得・DELETE時の接続エラーを模擬 | 後続処理を中止し、エラーを記録して非0の終了コードを返す |
| エラーを解除して再実行 | 残っている古いデータが削除され、保存期間内のデータは残る |
| ロック待ち時間超過・デッドロックを模擬 | 設定回数以内で再試行し、上限到達時は異常終了する |
| DBではコミット済みだが成功応答が得られない状態を模擬 | 結果不明をログに残し、その単位を成功確認済み件数に加えない。再実行で残りを処理できる |

ロールバックの確認では、DELETE後に例外を発生させ、セッションを取り直して未確定の削除が取り消されたことを確認する。

### 8.3 実環境での検証

SQLiteと例外の模擬で確認できるのはアプリ側の処理である。実際のDBロック・切断検知・ロック解除・コミット中の通信障害は、実稼働と同じDBエンジンのテスト専用環境で検証する。

| 検証対象 | 確認事項 |
| --- | --- |
| 日時・性能 | 保存期間の境界とDB日時の比較、実行計画、分割件数・全体上限5分の妥当性 |
| DB競合・障害 | ロック待ち・デッドロック時の再試行と異常終了、接続・通信タイムアウト、切断時のロールバックとコミット結果不明の扱い |
| 通常操作との並行実行 | 取り込み・読み取り・同一メールの更新や削除。画面側で保存時に対象が消えても未処理の例外にしないこと |
| systemd | 上限超過時の停止・失敗ログ・再実行、WSL停止中の実行漏れが次回起動後に補われること |

## 9. 未確定事項と事前確認

合意済みの要件は2章、具体的な処理方針は4～7章に示す。残る確認・確定事項は以下のとおり。

| 項目 | 確認・確定する内容 |
| --- | --- |
| 実稼働DB | 製品・バージョン・ストレージエンジン・分離レベル、実テーブルの定義とインデックスを確認する |
| 日時基準 | Power Automateが実際に保存する日時を確認し、削除基準日時との比較方法を決める |
| 実行環境 | WSL / systemdの設定と利用可否、実行ユーザー・配置先、定期・手動実行が同一WSL内であることを確認する |
| ロックファイル | 共通の絶対パス、ディレクトリとファイルの権限を確定する |
| 待機・停止の設定 | 全体上限5分を考慮し、DBの再試行回数・待機時間・ロック待ち時間、接続・通信タイムアウト、停止猶予の具体値を決める |
| 導入時の性能調整 | 分割件数の初期値1,000件と暫定の全体上限5分を実測で確認し、必要に応じて調整する |
