# メール取得・取り込みバッチの提案

## 1. 目的と基本方針

Power AutomateとOutlookによるメール取得・本文解析・CSV経由のMySQL登録を、WSL上のPythonバッチに置き換える。アプリ更新による動作不安定とOutlookの起動操作への依存を減らす。受信量は1日数百件で、サーバーには大量の過去メールが残っている可能性がある。

本資料は実装前の提案書である。今回の作業は文書整備までとし、コード、マイグレーション、テスト、定期実行設定は作成しない。

| 項目 | 合意済みの方針 |
| --- | --- |
| 配置・実行 | 同じリポジトリ内に取り込み処理を置き、Flask独自コマンドとしてWebサーバーと別プロセスで実行 |
| メール取得 | 当初はPOP（995、SSL/TLS）。将来IMAPへ拡張できる構造 |
| サーバーへの操作 | 削除・移動はしない。取得に伴う既読化は許容し、既読状態は処理済み判定に使わない |
| メール種別 | 設定に定義された有効な種別を共通処理で扱う |
| 中間データ | 本文と必要なヘッダーをSQLiteに保存。業務パース結果はメモリ上で登録処理へ渡す |
| 添付ファイル | 本文だけを処理し、添付は無視してログに記録。添付の有無でメールを対象外にしない |
| 保存先 | 業務データは既存モデル経由でMySQL、メールデータと取得・処理履歴はSQLite |
| 重複防止 | 各業務テーブルのmessage_idにUNIQUE制約。ID欠落は登録せずログに記録 |
| 並行実行 | バッチ同士は直列化し、Webアプリ利用とは並行させる |
| メールデータ保存期間 | 保存完了から30日で、処理状態にかかわらず本文・ヘッダーを削除。未登録のまま期限切れになることを許容 |
| 定期実行 | systemd.timerとserviceで一括コマンドを起動 |

本資料の「メールデータ」は、再パース用に保存する本文と必要なヘッダーを指す。CSVや実メールの.emlファイル、添付を含む完全な原文は保存しない。

直近30日以内を取得対象とする方向で検討する。具体的な設計案は2〜6章、テスト方針は7章、未確定事項と確定時期は8章に示す。コマンド名・ファイル名・設定形式は案とする。

## 2. 全体構成と責務

### 2.1 コマンド

```text
flask mail fetch
  接続 → UIDL一覧取得 → ヘッダーによる対象判定
    → メール全体の取得・本文抽出 → SQLiteにメールデータと取得履歴を同時保存

flask mail import
  SQLiteの保存済み本文・ヘッダー → 種別別パース・検証
    → MySQL登録 → SQLiteの処理状態更新

flask mail cleanup
  保存期間と状態を確認 → 削除対象のメールデータを削除

flask mail run
  fetch → import → cleanup
```

定期実行はrun、個別操作はfetch／import／cleanupを使う。importは保存済みメールデータをパースし、辞書などで登録処理に渡す。

### 2.2 機能の境界

| 機能 | 責務 |
| --- | --- |
| 取得クライアント | 接続・認証、取得元識別情報・ヘッダー・メッセージ全体の取得 |
| 対象判定 | 履歴・受信日時・種別設定による振り分け |
| メール解析 | ヘッダー・MIME・文字コードを扱い、本文を取り出す |
| 業務パーサー | メール形式ごとの項目抽出・検証・変換 |
| 種別別ハンドラー | パーサーと登録処理の組み合わせを提供 |
| DB登録 | 既存モデルによる保存と重複時の処理 |
| 履歴・メールデータストア | SQLiteへのメールデータ・履歴の保存・読み込み・整理 |
| 進行管理・CLI | 共通の処理順序・失敗の制御と、コマンド引数の受け取り |

メイン処理は問い合わせ・求人の項目やテーブルを直接判断せず、設定から選んだハンドラーを呼ぶ。同じアカウントへの接続・取得は種別間で共有する。既存のパーサー・登録先を使う種別は設定追加で対応し、新しい本文形式や登録先には必要なPython処理・モデル・マイグレーションを追加する。

責務をテスト可能に分け、クラス・ファイルの分割は実装規模に合わせる。配置案は付録Aに示す。

### 2.3 将来のIMAP対応

取得クライアントは取得したメッセージ・ヘッダー・取得元情報を共通形式で返し、業務パースと登録をプロトコルに依存させない。SQLiteでは共通の処理状態と方式固有の識別情報を分ける。

| 方式 | 固有の識別情報 |
| --- | --- |
| POP | アカウント、UIDL |
| IMAP | アカウント、フォルダー、UIDVALIDITY、UID |

IMAP用のSQLiteスキーマ・取得方法は対応時に設計し、未使用のカラムは先に作らない。方式変更時の再取得は、MySQLの各メールテーブルのmessage_idで二重登録を防ぐ。

## 3. 取得と対象判定

### 3.1 POPの取得履歴

POPのUIDLで得たIDをSQLiteに保存し、アカウントとの組み合わせで一意に管理する。接続ごとに変わり得るメール番号は使わない。

UIDL一覧を履歴と照合し、未確認・再試行対象だけヘッダーを読む。期間・種別条件に合えば本文を抽出して保存し、対象外も判定を記録する。取得完了は履歴の存在ではなく状態で判定する。

POPは日付検索ができないため、初回は大量の過去メールのヘッダー確認を許容する。1通ずつ結果を確定し、途中停止後は未確認・再試行分から再開する。以降もUIDL一覧は取得するが、確認済みのヘッダー取得は省く。メール番号と日時の順序は仮定しない。

### 3.2 日時

期間判定は、利用中の受信サービスが付けた信頼できるReceivedヘッダーを使う案とする。複数ある場合の選定は実メールで確認する。Dateと本文日時は受信日時と同一とは限らない。

実行開始時に基準時刻を1回確定し、タイムゾーンをそろえて判定する。取得判定用日時と業務テーブルのreceived_atは別に定義し、後者は現行の保存値との整合を確認する。30日条件の境界、不正日時、保存済みメールデータの再処理への適用は未確定とする。

### 3.3 本文抽出と添付の扱い

fetchでMIME解析・文字コード復号・本文選択を行い、importには保存済み本文と必要なヘッダーを渡す。本文のテキスト／HTMLの選択方法は第1段階で確定する。

添付があっても本文は通常どおり取り込む。添付パートを本文に混ぜず、内容の解析・展開・ファイル保存・DB登録は行わない。無視したことを内部IDと添付件数付きでログに記録し、ファイル名や添付内容は出力しない。

POPでは通常、添付を含む全体を取得してから本文を抽出する。SQLiteへの保存容量は減るが、取得通信量は減らない。抽出に失敗した場合は取得完了にせず、履歴に失敗理由を残して再取得できるようにする。

## 4. 種別設定とパーサー

### 4.1 設定の分離

| 内容 | 管理場所 |
| --- | --- |
| アカウント・接続先・認証情報 | 環境変数などの実行環境設定 |
| 種別名、有効／無効、送信元、件名条件、ハンドラー名 | 専用のルール設定ファイル |
| 本文の抽出・検証・変換 | 形式ごとのPythonパーサー |

ハンドラー名は用意した対応表から選ぶ。設定形式はTOMLを候補とし、例を付録Bに示す。複数一致はログに記録して保留する案とする。振り分け規則と設定変更時の再判定は8.3節で確定する。

### 4.2 パース規則

contact.pyやjob.pyに、開始・終了の文字列や正規表現を使った項目抽出をPythonで記述する。パーサーは本文と必要なヘッダーを受け取り、登録用データを返す。通信・ファイル・DB操作は行わない。

必須見出しの欠落や曖昧な範囲は解析失敗とし、許可する空欄は項目ごとに定める。共通処理が必要になった場合はparsers/common.pyを作成する。

### 4.3 未定義パーサーなどの設定エラー

実行開始時に有効な種別の参照先を検証する。パーサーがない場合は種別名・パーサー名・理由をエラーログに出力する。ハンドラー・登録処理がない場合も同様とする。

該当メールは対象外や登録済みにせず、再試行可能な保留とする。本文未保存なら取得完了にしない。正常な種別は継続し、実行結果は非0とする。保留分の期限切れは5.4節に従う。

## 5. 保存・登録・排他制御

### 5.1 保存先と状態

| 保存先 | 内容 |
| --- | --- |
| MySQL | 問い合わせ・求人の業務データとMessage-ID |
| SQLite：メールデータ | 本文（テキスト、必要に応じHTML）、Message-ID・件名・送信元・Date・Receivedなど必要なヘッダー、受信判定用日時、保存完了日時 |
| SQLite：取得・処理履歴 | アカウント・方式・取得元識別情報・種別・状態・取得日時・エラー |

メールデータと履歴は別テーブルなどで関連付け、本文・ヘッダーの削除後も取得済み識別情報を保持する。Receivedなど複数存在するヘッダーは、必要な順序・値を失わない形で保存する。

状態は、対象外、保存済み・未処理、登録済み、重複、ID欠落、設定エラー保留、処理失敗、期限切れを区別する。本文未保存の取得・抽出失敗と、保存後の業務パース・登録失敗は区別し、それぞれfetchとimportで再処理する。

### 5.2 重複防止とスキーマ変更

ContactEmailとJobEmailにmessage_idを追加し、それぞれUNIQUE制約を設定する。同じ内容でも別Message-IDなら登録する。各テーブル間の一意性は保証しない。

既存行のためNULLを許可するが、新規取り込みではID欠落・空欄をログと履歴に記録してスキップする。IDはヘッダーの折り返し・周囲の空白を扱い、大文字・小文字を勝手に変えない。カラム長・照合順序・インデックスと不正IDの扱いを実装前に確認する。

重複防止は事前照会だけに頼らずDB制約でも保証し、他の制約違反と区別する。MySQLはFlask-Migrate／Alembicで変更する。SQLiteは未作成時の初期化とスキーマバージョンの記録を行う案とし、MySQLとは別管理にする。

### 5.3 途中失敗と再実行

SQLiteでは、1通分の本文・ヘッダー保存と取得済み履歴を同じトランザクションで確定する。失敗時は両方をロールバックし、次回再取得する。メール取得・解析中はSQLiteの書き込みトランザクションを保持しない。

MySQLとSQLiteは別トランザクションのままで、次の順序を守る。

1. MySQLへの登録をコミットする。
2. 成功を確認してからSQLiteを登録済みに更新する。
3. 両者の間に停止した場合やコミット結果が不明な場合は、再実行時にMessage-IDで登録結果を確認し、状態を修復する。

業務パースは保存済み本文からやり直す。MIME解析・文字コード・本文選択の修正には、UIDLを指定した明示的な再取得を用意する。サーバーにないメールは再取得できず、再取得しても登録済みMySQLデータは上書きしない。

### 5.4 保存期間と整理

cleanupは本文・ヘッダーの削除と履歴更新を同じSQLiteトランザクションで行う。期間の基準は次のとおり。

| 対象 | 期間・扱い |
| --- | --- |
| 新規取得 | 受信から30日以内を対象とする案。計算・境界は未確定 |
| 保存済み本文・ヘッダー | 処理状態にかかわらず、保存完了日時が実行開始時刻の30日前以下なら削除。再処理だけで保存日時を更新しない |
| UIDL・処理結果 | サーバーにメールがある間は保持し、自動再取得を防ぐ |
| 本文未保存の失敗・保留 | 期限基準は第2段階で確定 |

未完了分を削除した場合は種別・件数・内部IDをログに残し、履歴を期限切れにする。以降は自動取得・再処理をせず、必要時のみ明示的に再取得する。未登録のまま期限切れになることは許容する。

サーバーから消えたUIDLの履歴は、全件の一覧取得に成功した際に整理する。ただし、保存期限内の未処理データと再処理情報は残す。SQLiteの削除領域はDB内で再利用されるため、ファイル縮小の要否は別途判断する。

### 5.5 並行実行とDBトランザクション

| 対象 | 方針 |
| --- | --- |
| バッチ同士 | 同一WSL内の共通ファイルロックで直列化。fetch・import・cleanup・run・履歴の整理を対象にする |
| Webアプリとの並行操作 | 別々の接続・セッション・トランザクションを使い、競合はMySQLに調整させる |

runは全体でロックを保持し、内部処理で二重取得しない。Webアプリはこのファイルロックを使わない。

MySQL / InnoDBを前提に、登録はメール1通ごとの短いトランザクションにする。取得・SQLiteからの読み込み・パース・検証は事前に終え、通信や本文解析の間にMySQLのロックを保持しない。重複時は既存行を更新せず、利用者のメモ・フラグを上書きしない。

通常のSELECTは一般的な分離レベルでは登録と並行できるが、競合する書き込みには待機が起こり得る。明示的なテーブルロックは設けず、SQL・インデックス・分離レベルに応じたロック動作を確認する。定期削除との競合も同じ前提で検証する。

ロック待ち時間超過・デッドロック時は、その1通のトランザクション全体をロールバックし、回数・待機時間を制限して再試行する。上限到達時は失敗を記録し、メールデータは保存期限まで残す。待機・再試行の具体値、ロック取得失敗時や後続メールへの継続方針は8.3節に従って確定する。

## 6. 定期実行と運用

systemd.timerからType=oneshotのserviceを起動し、flask mail runを実行する。serviceには実行ユーザー、作業ディレクトリ、仮想環境、Flaskアプリ・実行環境、設定の読み込み方法、実行時間上限を明示する。

初回fetchは手動実行などで十分な時間を確保し、完了後に定期運用へ移る。初回と定期実行の時間上限は別に定める。

timerはOnCalendarとPersistent=trueを使い、停止中に予定時刻を過ぎていれば次回有効化時に1回実行する。Windows・WSLの停止やスリープ中の実行、自動起動、WSLの常時稼働は保証しない。Persistentは失敗時の再試行機能ではない。実行間隔と時間上限は取得性能の実測で決める。

ログは標準出力・標準エラーからjournalに収集する。種別別の件数、結果・失敗理由、メールデータを特定する内部ID、所要時間を記録し、本文全体・認証情報は出力しない。

移行時はPower Automateの停止位置と新方式の取り込み開始位置を合わせる。既存行のMessage-IDはNULLのため、30日条件だけでは既存分の二重登録を防げない。必要に応じて既存分のUIDLを初期登録する。既存のCSV取り込みはモデル・変換規則の参考とし、変更範囲は実装時に判断する。

[メールデータ定期削除バッチの提案](email-retention-batch-proposal.md)とは独立した計画とし、導入時に日時と並行操作の整合を確認する。

## 7. テスト方針

重点は正しい項目抽出、二重登録防止、失敗後の安全な再処理とする。

| 検証対象 | 最低限の確認 |
| --- | --- |
| メール解析・業務パーサー | MIME・文字コード・本文選択、日本語・HTML・複数行・空欄・見出しとIDの欠落 |
| 対象判定 | 取得済み／再試行対象、種別条件、期間境界、不正日時 |
| 添付のあるメール | 添付を本文に混ぜず本文だけを登録し、添付を無視したログを残す。SQLite・ファイル・MySQLに添付を保存しない |
| 種別設定・ハンドラー | 複数種別の処理、未定義参照時のログ・保留・正常分継続・非0終了、保存期限内の修正後の再処理 |
| POPクライアント | 取得手順、削除命令を送らないこと、取得失敗 |
| 初回fetch | 多数の対象外メールの判定履歴を残し、途中停止後は未確認分から再開できること。再実行時に確認済みのヘッダー取得を省くこと |
| メールデータ・SQLite | 保存・復元・状態更新、本文・ヘッダーと取得済み履歴の同時コミット／ロールバック、保存期限内の未処理情報保持 |
| cleanup | 保存完了から30日の境界、全状態の本文・ヘッダー削除、未完了分の期限切れログ、UIDLと期限切れ状態の保持、自動再取得の抑止、個別実行とrunからの呼び出し |
| MySQL登録 | 一意制約、他の制約違反との区別、ロールバック、既存行を上書きしないこと |
| 進行管理 | SQLite保存失敗とMySQLコミット直後の停止からの復旧、本文抽出の誤りに対する明示的な再取得、コマンド引数・終了結果、多重起動防止 |

パーサー・判定は通信・DBなし、SQLiteは一時DBで検証する。MySQL固有の制約・照合順序・ロック動作はテスト用MySQLで確認する。ロック待ち・デッドロック時の制限付き再試行とメールデータ保持も対象にする。

実サーバーの認証・取得性能、アプリの参照・メモ更新や定期削除との並行動作、timer・ログは結合・導入時に確認する。自動テストと実環境で確認できた範囲は分けて記録する。テストは実処理を呼び出し、メールデータサンプルには架空の個人情報を使う。

## 8. 段階計画と未確定事項

### 8.1 進め方

複数セッションに分け、各段階でテスト結果・未解決事項・次の前提を確認する。1段階を必ず1セッションで終える必要はない。共有機能は必要な範囲から実装して拡張する。

問い合わせ・求人の匿名化サンプルを準備し、改行・MIME構造・本文形式を確認する。第1段階はサンプルから本文・ヘッダーを一時SQLiteに準備し、POPなしで検証する案とする。テスト用DBのマイグレーション検証と本番適用は分ける。

### 8.2 作業と完了目安

| 段階 | 作業範囲 | 完了目安 |
| --- | --- | --- |
| 1：パース・登録 | 種別設定、ハンドラー、メール解析、パーサー、モデル・マイグレーション、1通単位の登録・DB競合処理、SQLiteの本文・ヘッダー・状態管理、import | サンプルを正しく登録でき、ID欠落・設定エラー・重複・登録失敗後の再処理をテストできる |

テストファイルも対応例であり、ケースごとに分割する必要はない。fixturesの.emlはメール解析テスト用の架空サンプルで、実メールの保存方式とは別である。

実環境設定とデータはソースから分離する。以下は例であり、絶対パス・権限は導入時に定める。

```text
実環境設定用ディレクトリ/
├── mail-ingest.env            # 接続先・認証情報・設定パスなど
└── rules.toml                 # 実際の種別・対象アドレス・件名とハンドラーの対応

WSL内のデータ保存用ディレクトリ/
└── state.sqlite3              # 本文・必要なヘッダーと取得・処理履歴
```

これらはWeb公開先とリポジトリの追跡対象から外し、環境設定で配置先を指定する。SQLiteはWSLのLinuxファイルシステム上に置く。systemd用ファイルもリポジトリ内ではテンプレートとして管理し、実環境への配置・有効化は導入作業として行う。

### Git管理と.gitignoreの方針

| 対象 | Git管理 |
| --- | --- |
| 認証情報を含む `mail-ingest.env` | 対象外 |
| 実際のアドレス・運用条件を含む `rules.toml` | 対象外 |
| SQLite本体と付随ファイル（WAL、SHM、ジャーナルなど） | 対象外 |
| メールデータを含むSQLiteのバックアップ・調査用エクスポート | 対象外 |
| ファイルログ・ロックファイル（作成する場合） | 対象外 |
| 秘密情報を含まない設定例（`rules.example.toml` など） | 管理する |
| 架空データのテスト用 `.eml` | 管理する |
| systemdテンプレート・マイグレーション | 管理する |

現在は.envのみ除外済みで、新しい保存先は実装時に.gitignoreへ追加する。実行時データは専用ディレクトリ単位、設定は配置パスで除外する。*.emlの一律除外は避け、設定例とテストデータがGit管理できることも確認する。
